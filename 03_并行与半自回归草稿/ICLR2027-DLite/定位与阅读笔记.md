# DLite：Agentic 工作负载中的 token 级推测解码

## 2. 应该放在哪一类？

**主要贡献放在 `03_并行与半自回归草稿`；交叉标签是 Agentic token-level SD、长上下文、草稿 KV 开销和训练对齐。**

它服务于 Agent 的长上下文、多轮调用，但预测单位仍是下一批 token。它没有把未来工具调用或整个 Agent 动作提前执行。因此需要区分：

| 层面 | 代表问题 | DLite 的位置 |
| --- | --- | --- |
| token 级 | 一次 LLM 调用内部如何更快生成文本 | 属于这一层，改进 drafter |
| 服务级 | 多轮请求如何调度、复用前缀、分配验证预算 | 涉及这类成本，但主要方法是草稿架构 |
| 动作／工具级 | 预测下一次调用或工具结果，验证后提交或回滚 | 不是 DLite 本文的方法 |

`history-free` 的主体是**草稿模型**，不是目标模型或整个 Agent。目标模型仍处理完整上下文，草稿复用其已经编码了上下文的隐藏状态。

## 3. 三个核心设计

### 3.1 不让草稿端再次独立维护长历史

作者观察到，多轮 Agent 场景中的上下文不断增长，既影响现有草稿模型的接受长度，又产生历史 KV 更新与维护成本。DLite 直接消费目标上下文隐藏状态，把草稿预测转为局部任务。

### 3.2 并行骨干加轻量顺序头

并行骨干控制整块候选的起草成本；轻量顺序头补充块内因果依赖。它不是“所有未来 token 完全独立预测”，也不是没有任何顺序执行。

### 3.3 分两阶段训练

先用结构更接近的 history-aware teacher 作为优化桥梁，再直接向目标模型对齐。稳定阶段结合 token 交叉熵与分布差异目标。需要分别检查架构变化和训练策略的消融收益。

## 4. 数字应该怎样读？

正文报告的 acceptance length 约 2–6 是**每轮接受长度**，不能当成 2–6 倍端到端加速。摘要的“最高 70%”也不能直接改写成所有任务上快 70%。

论文 Table 3 的两个具体例子：

| 目标模型／任务 | DSpark 加速 | DLite 加速 | DSpark 接受长度 | DLite 接受长度 |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-4B／SWE-bench | 1.64× | 2.68× | 1.89 | 3.15 |
| Qwen3-8B／SWE-bench | 1.60× | 2.74× | 1.94 | 3.19 |

这些是作者在 H800 和指定模型设置下报告的结果，并非本地复现。不同任务的收益应分别阅读。

## 5. Agentic 评测的边界

附录 implementation details 明确限定了抽样设置：SWE-bench 使用 50 个长输入 prompt；AgentLongBench 使用 50 个 64K setting prompt；MemoryAgentBench 抽取部分问答作为独立长上下文输入；BFCL 使用 41 个 multi-turn-long-context session，并聚合输入超过 32K 的模型调用。

尤其是 **BFCL 不计工具执行时间**。因此不能把这些数字直接称为完整 Agent 任务的总完成时间加速，也不能据此声称 Agent 解决任务的成功率提高。

## 6. 与现有文献的比较问题

1. 对比 DFlash、Domino、DSpark：块内依赖如何表达？草稿的历史输入与 KV 如何维护？
2. 对比 EAGLE-3：使用哪些目标隐藏状态？自生成状态与训练输入是否匹配？
3. 对比 DLoop：DLite 改变一次起草的结构和历史依赖，DLoop 改变一次目标验证前的起草轮数；是否可组合需要实验，不能仅凭结构想当然。
4. 对比 SpecSplice、AgSpec 等 Agentic 草稿：DLite 通过学习表征起草，检索草稿通过复用历史片段起草，二者的瓶颈和适用数据不同。
